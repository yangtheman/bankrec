## Project Overview

BankRec is a cross-platform Electron desktop application for managing and reconciling bank transactions. It uses AES-256-GCM encryption for all sensitive data, with encryption keys stored securely in the OS keychain (via Keytar) or as an encrypted fallback file.

## Development Commands

### Running the Application

```bash

yarn install

# Start development (compile TypeScript + build CSS + launch app)
```

## Architecture

### Electron 3-Process Architecture

**Main Process** (`src/main/main.ts`):
- Handles all database operations via `EncryptedDatabase` class
- Manages IPC handlers for renderer communication
- Controls encryption key lifecycle via `EncryptionKeyManager`
- Handles file dialogs, import/export, and security policies

**Preload Script** (`src/preload/preload.ts`):
- Provides secure IPC bridge via `contextBridge.exposeInMainWorld("electronAPI", ...)`
- Acts as the only communication channel between renderer and main process
- Exposes methods for data operations, transactions, reconciliation, and encryption key management

**Renderer Process**:
- `src/renderer/app.js`: Main application logic (vanilla JavaScript)
- `src/views/index.html`: UI templates
- `src/styles/`: Tailwind CSS + DaisyUI styling

### Security Architecture

**Encryption System**:
- All sensitive data encrypted using AES-256-GCM (via Node.js crypto module)
- `EncryptionKeyManager` (`src/main/encryption-manager.ts`): Handles key generation, storage, and retrieval
  - Primary: Stores keys in OS keychain via `keytar` library
  - Fallback: Encrypted file storage at `~/Library/Application Support/BankRec/secure/.keystore` (macOS) or `%APPDATA%/BankRec/secure/.keystore` (Windows)
- `EncryptedDatabase` (`src/main/db.ts`): Wraps Better-SQLite3 with transparent encrypt/decrypt on sensitive fields
  - Encrypts: user names, transaction descriptions, categories
  - Encryption format: `iv:authTag:encrypted` (hex-encoded)

**Validation Layer** (`src/renderer/validation.ts`):
- All user inputs validated before database operations
- Functions: `validateUserData()`, `validateTransactionData()`, `validateFilePath()`, `sanitizeString()`
- Path traversal protection (blocks `..` and validates absolute paths)
- String sanitization removes null bytes and control characters
- `RateLimiter` class protects export operations (5 exports per 5 minutes)

**Web Security**:
- Main process prevents navigation to external URLs
- Window opening blocked via `setWindowOpenHandler()`
- Context isolation enabled, node integration disabled

### Database

**Technology**: Better-SQLite3 (embedded SQL database)

**Location**:
- macOS: `~/Library/Application Support/BankRec/data/bankrec.db`
- Windows: `%APPDATA%/BankRec/data/bankrec.db`
- Configurable via `ConfigManager` (`src/main/config-manager.ts`)

**Configuration**:
- WAL (Write-Ahead Logging) mode enabled for better concurrency
- Foreign keys enabled
- Schema initialized in `initializeTables()` method

**Tables**:
- `users`: User information (encrypted names)
- `transactions`: Transaction records (encrypted descriptions/categories)
- `categories`: Custom transaction categories (encrypted names)

**Transaction Schema**:
```typescript
{
  id: string,           // UUID (generated by database)
  user_id: number,
  date: string,         // ISO format (YYYY-MM-DD)
  description: string,  // Encrypted (mapped to "payee" in frontend)
  amount: number,       // Stored as INTEGER (cents)
  type: 'debit' | 'credit',
  category: string,     // Encrypted, nullable
  check_number: string, // Optional, nullable
  is_reconciled: 0 | 1, // SQLite boolean
  account_id: string    // Nullable (for future multi-account support)
}
```

## Key Patterns

### IPC Communication Pattern

All main-renderer communication follows this structure:

1. Renderer calls `window.electronAPI.*` method (exposed via preload)
2. Preload forwards to main via `ipcRenderer.invoke()`
3. Main process validates inputs using `validation.ts` functions
4. Main process performs operation and returns standardized response: `{ success: boolean, error?: string, ...data }`

**Example Flow** (saving transaction):
```
renderer/app.js → window.electronAPI.saveData(data)
preload.ts → ipcRenderer.invoke('save-data', data)
main.ts → ipcMain.handle('save-data', ...) → validates → db.createTransaction() → returns {success: true}
```

### Database Access Pattern

**Critical Rules**:
- NEVER access `db.db` (raw SQLite connection) directly
- ALWAYS use `EncryptedDatabase` class methods
- Sensitive fields auto-encrypt on write, auto-decrypt on read
- Use prepared statements with parameter binding (NEVER string concatenation)

**Field Mapping** (Frontend ↔ Database):
- Frontend `payee` ↔ Database `description`
- Frontend `reconciled` ↔ Database `is_reconciled`
- Frontend `accountId` ↔ Database `account_id`
- Frontend `checkNumber` ↔ Database `check_number`

### Adding New Features

**Adding IPC Handler**:
1. Add handler in `src/main/main.ts`: `ipcMain.handle('my-action', async (_event, ...args) => { ... })`
2. Expose in `src/preload/preload.ts`: `myAction: (...args) => ipcRenderer.invoke('my-action', ...args)`
3. Validate inputs using `validation.ts` functions
4. Return `{ success: boolean, error?: string }` structure

**Adding Database Method**:
1. Add method to `EncryptedDatabase` class in `src/main/db.ts`
2. Use `this.encrypt()` for sensitive data before storing
3. Use `this.decrypt()` when retrieving sensitive data
4. Use prepared statements: `this.db.prepare(sql).run(params)`
5. Add test in `src/main/db.test.ts`

**Adding Validation**:
1. Add function to `src/renderer/validation.ts`
2. Export for use in main process
3. Add test in `src/renderer/validation.test.ts`
4. Call from IPC handlers before database operations

## Important Notes

**Native Dependencies**:
- `better-sqlite3` requires native compilation
- Prerequisites:
  - macOS: Xcode Command Line Tools (`xcode-select --install`)
  - Windows: Visual Studio Build Tools

**Encryption Key Management**:
- User MUST save encryption key during onboarding
- Key required for export/import operations
- Lost keys cannot be recovered
- Key stored in OS keychain (Keychain Access on macOS, Credential Manager on Windows)

**DevTools**:
- Auto-opens in development (`NODE_ENV=development` or `!app.isPackaged`)
- To disable: modify condition in `src/main/main.ts:54-56`

**Testing Limitations**:
- Database tests (`db.test.ts`) require Electron environment and are excluded from Jest runs
- Use `yarn test:coverage` to see which modules have coverage

**Data Migration**:
- Schema migrations handled in `initializeTables()` with try-catch for existing columns
- Export/import uses password-protected encrypted files (`.enc` format)
- Import file size limited to 100MB

## Common Pitfalls

1. **Don't bypass encryption**: Always use `EncryptedDatabase` methods, not raw SQLite
2. **Don't skip validation**: All IPC handlers must validate inputs before processing
3. **Frontend/DB field names differ**: Remember the field name mappings (e.g., `payee` vs `description`)
4. **Database initialization timing**: Main process may retry database initialization if encryption key isn't ready yet (see `initializeDatabase()` retry logic)
5. **Currency storage**: Amounts stored as integers (cents) in database, displayed as formatted decimals in UI
6. **No string concatenation in SQL**: Always use prepared statements with parameter binding
